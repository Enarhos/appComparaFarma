## 2. AUTH-DELETE-01 — backend de eliminación de cuenta

Se implementó y desplegó el endpoint:

`POST /api/account?action=delete`

Principios confirmados:

- identidad resuelta exclusivamente desde el JWT validado;
- reautenticación obligatoria antes del borrado;
- cuentas con suscripción externa activa deben cancelarla antes;
- eliminación de datos personales y de identidad;
- preservación de inteligencia farmacéutica no personal;
- soporte de retry/resume cuando el proceso queda en `DELETION_PENDING`;
- RPC y tabla de control restringidos a `service_role`/`postgres`.

El backend fue mergeado mediante PR #108. Commit de merge en `main`: `7c29ea4`.

Producción validada con `/api/health`, confirmando el commit desplegado y dependencias operativas.

## 3. Incidente de Preview — `SUPABASE_ANON_KEY`

Durante el Gate 3 se detectó que `SUPABASE_ANON_KEY` en Vercel contenía un carácter Unicode inválido (em dash, U+2014), provocando error `ByteString` en la reautenticación por contraseña.

El hallazgo fue clasificado como infraestructura/configuración, no como defecto del diseño de eliminación.

Tras corregir la variable se reanudó la validación y el backend quedó apto para Producción.

## 4. AUTH-DELETE-02 — UX Web

Se agregó el flujo de autoservicio en Web:

- CTA `Eliminar cuenta` dentro de `/cuenta`;
- ruta `/cuenta/eliminar`;
- explicación de qué datos se eliminan y cuáles se conservan;
- ingreso de contraseña;
- confirmación final separada;
- llamada al backend `AUTH-DELETE-01`;
- cierre de sesión solo después de `200 OK`;
- redirección a Home tras el éxito.

El flujo no acepta `user_id` ni email desde el cliente como fuente de identidad.

## 5. AUTH-DELETE-02 — UX Mobile

Se agregó `DeleteAccountSheet` con dos pasos internos:

1. explicación + contraseña;
2. confirmación final irreversible.

El cierre/cancelación limpia contraseña, error y estado del flujo. El token se obtiene desde la sesión activa al momento del request y no se persiste en el componente.

Los datos locales del dispositivo (`favorites`, carrito/receta, historial, ubicación y alertas locales) se preservan porque no son datos sincronizados con la cuenta.

## 6. Hardening de seguridad del cliente

Se endurecieron Web y Mobile antes del push final:

- no se loguean excepciones crudas, password ni JWT;
- los mensajes del backend no se reenvían directamente al cliente;
- Web limpia la contraseña después de cada intento;
- Mobile limpia la contraseña al cerrar/cancelar y al completar con éxito;
- se mantuvieron mensajes de error estables y controlados.

Commit de hardening: `4db94e7`.

## 8. Política de privacidad

Se actualizaron:

- `docs/privacy-policy.html`;
- `web/src/app/privacidad/page.tsx`.

La política ahora:

- deja de afirmar de forma absoluta que no se recopilan datos personales;
- explica que una cuenta puede asociar email, autenticación, alertas, feedback y suscripción;
- incorpora una sección explícita de eliminación de cuenta;
- establece que el borrado es permanente y no una anonimización;
- explica que la inteligencia farmacéutica no personal se conserva;
- referencia la Ley N.º 21.719 en lenguaje informativo de producto.

Commit: `6b5e6c3`.

## 9. E2E en Preview

Con una cuenta QA descartable se validó:

- login correcto;
- CTA `Eliminar cuenta` visible;
- flujo de dos pasos;
- contraseña incorrecta rechazada sin modificar la cuenta;
- contraseña correcta elimina realmente la cuenta;
- sesión del cliente queda cerrada;
- intento posterior de login con las mismas credenciales falla;
- no quedan filas residuales para el usuario QA en `auth.users`, `profiles` ni `account_deletion_requests`;
- `medications`, `price_history` y `subscription_plans` permanecen intactos.
