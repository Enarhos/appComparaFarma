3. Bioequivalencia — causa raíz y cierre

Se confirmó que la mezcla entre bioequivalentes y no bioequivalentes no era un problema de renderizado Web sino de Domain/API.

Causa raíz: mergeDuplicates() agrupaba resultados únicamente por matchKey, permitiendo fusionar productos con igual medicamento/dosis/cantidad pero distinta clasificación de bioequivalencia.

Corrección inicial: la deduplicación pasó a distinguir bio:true, bio:false y bio:unknown.

Posteriormente esta lógica quedó incorporada dentro de presentationKey, manteniendo la bioequivalencia como partición obligatoria.

Tests de Domain, API y Web quedaron verdes y la separación fue confirmada en Producción.

4. Ficha de medicamento — slugs y compatibilidad

Después del fix de bioequivalencia apareció un problema en las fichas de medicamento: dos resultados podían compartir matchKey pero tener distinta bioequivalencia, haciendo ambiguo el hash del slug.

Se implementó una evolución compatible del esquema de slugs:

- Gen 3: hash basado en presentationKey.
- Gen 2: fallback matchKey + bioequivalencia.
- Gen 1: fallback legacy basado solo en matchKey.

Los slugs históricos continúan resolviendo mediante fallback y desambiguación por la parte humana del slug.

El caso legacy reportado de Paracetamol quedó funcionando correctamente.

5. Product Identity — Fase 1

5.1 Problema

Una búsqueda de Omeprazol evidenció que productos comercialmente distintos estaban fusionados bajo una misma tarjeta. El caso crítico fue Omeprazol 20 mg x30 de marcas Ascend, OPKO y CuraeSpring, cuyos precios se mezclaban aunque correspondían a productos diferentes.

5.2 Modelo aprobado

Se mantuvo matchKey como identidad farmacológica amplia y se introdujo presentationKey como identidad de producto comercial.

Conceptualmente:

presentationKey = matchKey + bioequivalencia + identidad comercial

Ejemplos:

- omeprazol|20mg|30|bio:false|brand:ascend
- omeprazol|20mg|30|bio:false|brand:opko
- omeprazol|20mg|30|bio:false|brand:curaespring

mergeDuplicates() pasó a agrupar por presentationKey.

matchKey no cambió de semántica y continúa siendo utilizado por historial, alertas, favoritos, tracking y CFM-ID.

5.3 Identidad comercial

Se agregó resolveCommercialIdentity() con política conservadora:

- Campo estructurado plausible → HIGH.
- URL de fuente confiable + identidad plausible → MEDIUM.
- Evidencia insuficiente → UNKNOWN.

Nunca se inventa una marca cuando no existe evidencia suficiente.

Se incrementó el cache mobile search_cache_v10_ → search_cache_v11_ por cambio de forma y cardinalidad de MedicationResult.

6. Hardening de identidad comercial

Una auditoría de datos reales detectó falsos positivos como detalleproducto, recubiertos, chile desde URL, blandas, 100ml, x30com, losartanhidroclorotiazida, ibuprofeno y omeprazol utilizados incorrectamente como identidad comercial.

Se implementaron reglas de plausibilidad para rechazar:

- ingredientes activos usados como marca;
- formas farmacéuticas;
- tokens de cantidad;
- run-ons anormalmente largos;
- tokens genéricos de URL;
- frases estructuradas que no representan una marca.

La extracción de marca desde URL quedó limitada a hosts explícitamente confiables; en esta fase, nuevo.easyfarma.cl.

Se preservaron marcas reales verificadas: Ascend, OPKO, CuraeSpring, Tapsin, Lomex, Corodin, Cozaar y Hyzaar.

En Producción, ninguno de los nueve tokens de ruido objetivo apareció como commercialIdentity en las búsquedas auditadas.

Residuales documentados, no corregidos en esta sesión:

- brand:pharma en un caso de Losartán/EasyFarma.
- actron600 en Ibuprofeno.

Se consideran deuda de bajo riesgo para una fase posterior.

7. Caché — investigación del falso bloqueo de Omeprazol

Después del primer deploy de Product Identity se observó temporalmente que Omeprazol seguía mostrando datos antiguos.

La investigación identificó tres capas de caché:

1. Redis/Upstash: cfsearch:<query>, TTL nominal 300 segundos.
2. Vercel Edge: s-maxage=300, stale-while-revalidate=60.
3. Next.js Data Cache Web: fetch con revalidate: 300 y revalidación perezosa.

No existía una key Redis permanentemente atascada. El backend estaba entregando datos nuevos; la percepción de staleness provenía principalmente de la revalidación perezosa de Next.js y de una respuesta cacheada de la herramienta utilizada durante la auditoría.

No se realizó invalidación manual de Redis.

Deuda de diseño pendiente:

- versionar namespace de caché API (por ejemplo cfsearch:v2:);
- considerar invalidación/versionado por deploy cuando cambia MedicationResult;
- documentar explícitamente el comportamiento de revalidación perezosa del Data Cache Web.

8. Product Identity — Fase 2 UX Web

Con la identidad comercial ya correcta en Domain/API, se implementó agrupamiento visual en Web para evitar mostrar una tarjeta completa por cada marca.

Arquitectura:

- Nivel superior: grupo por matchKey / presentación farmacológica.
- Nivel secundario: productos comerciales individuales por presentationKey.

Se agregaron:

- groupMedicationResultsByMatchKey().
- MedicationResultsGroup.
- CommercialProductRow.

Reglas UX:

- orden por menor precio;
- bioequivalencia como desempate, no como prioridad absoluta;
- cobertura como siguiente desempate;
- productos no identificados al final cuando existen alternativas identificadas;
- máximo inicial de 3 opciones en mobile y 5 en desktop;
- "Ver X opciones más" / "Ver menos";
- badge Bioequivalente solo para true;
- "Marca no identificada" con tratamiento neutro;
- detalle y Mi receta operan siempre sobre el MedicationResult individual, nunca sobre el grupo.

El QA Preview confirmó reducción importante de tarjetas de nivel superior, manteniendo cada producto comercial separado.

9. Bug OPKO — redirect loop

Durante QA de Fase 2 se encontró un bug preexistente: la ficha de Omeprazol/OPKO podía quedar indefinidamente en "Cargando ficha del medicamento…".

Causa raíz:

- presentationKey y hash Gen 3 eran estables;
- canonicalName podía variar entre búsquedas dependiendo de las farmacias que respondieran;
- la parte humana del slug cambiaba aunque la identidad fuese la misma;
- page.tsx redirigía cuando canonicalSlug !== slug;
- esto podía producir un loop de permanentRedirect entre variantes cosméticas del mismo producto.

Fix:

resolveMedicationBySlug() ahora retorna needsRedirect.

- Gen 1 / Gen 2 legacy → needsRedirect: true.
- Gen 3 actual → needsRedirect: false aunque cambie la parte humana del slug.

page.tsx redirige según needsRedirect y no por comparación completa de strings.

El fix se integró junto con Fase 2.
