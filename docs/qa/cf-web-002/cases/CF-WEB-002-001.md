# CF-WEB-002-001 — El resolver vuelve a buscar con una consulta más angosta que la que generó el enlace

| Campo | Valor |
|---|---|
| **Severidad** | **P1** — navegación rota desde resultados vigentes |
| **Clasificación** | `NAVIGATION_BROKEN` (`NOT_FOUND`) |
| **Causa raíz** | #1 — recuperación |
| **Medido** | 2026-09-01, `origin/main` `5a1e7e3` vs branch, corpus congelado en `raw/baseline/` |
| **Impacto en la línea base** | **16 de 128** enlaces (12,5 %) |

## Comportamiento observado

`resolveMedicationBySlug` reconstruía el texto de búsqueda con la parte legible
COMPLETA del slug —es decir, con el `canonicalName` entero— y se lo mandaba a
`/api/search`. Eso no es una búsqueda más precisa: es una consulta **distinta y
más angosta**, y los 9 buscadores de farmacia responden a ella con otro conjunto
de productos.

Medición directa contra producción (2026-08-31):

```
/api/search?q=tapsin                              → 137 tarjetas
  incluye "Tapsin X 6 comprimidos Noche (Maver)"  ← la tarjeta que genera el enlace
/api/search?q=tapsin x 6 comprimidos noche maver  →  24 tarjetas
  cleanQuery() la reduce a "tapsin noche maver"
  la tarjeta NO está entre ellas
```

El producto que **existía al generar el enlace** desaparecía del conjunto de
candidatos al resolver ese mismo enlace, segundos después. La ficha respondía
"Medicamento no encontrado" con el producto perfectamente disponible.

`cleanQuery()` no tiene la culpa: su trabajo es maximizar recuperación
(`docs/technology/domain/`, CF-SEARCH-002). El defecto es pedirle que recupere a
partir de un nombre de producto completo, que es justo el peor texto posible
para un buscador de catálogo.

## Enlaces afectados en la línea base

`NOT_FOUND` por consulta: tapsin 3 · metformina 3 · betametasona 2 ·
clotrimazol 2 · glicerina 2 · diclofenaco 1 · omeprazol 1 · clorfenamina 1 ·
cetirizina 1.

Los **7 enlaces muertos de CF-QA-001** (QA-SEARCH-002) se reprodujeron uno por
uno contra el código actual: **7 de 7 seguían muertos** (`legacyResolved: 0`).

## Corrección

Escalera de recuperación en `retrievalQueriesForSlug()`: primero la **cabecera
de marca/principio activo** del nombre —leída con `brandHeadTokens()` de
`@comparafarma/domain`, la misma regla que `matchKey()` usa, sin duplicarla— y
después el nombre completo como segundo intento.

```
tapsin-x-6-comprimidos-noche-maver-3a14ey6g56zgt
  → ["tapsin", "tapsin x 6 comprimidos noche maver"]
```

No es "reintentar hasta que funcione": ampliar el conjunto de candidatos solo
puede AGREGAR productos que no matchean el hash. El criterio de identidad es
idéntico en todos los intentos, y **en cuanto una consulta produce algún
candidato con el hash pedido se corta** — incluso si el resultado es ambiguo.
Seguir probando consultas hasta que quede una sola candidata sería elegir el
producto por conveniencia.
