# CF-WEB-002-004 — Soft-404: una ficha irresoluble responde HTTP 200

| Campo | Valor |
|---|---|
| **Severidad** | P2 — semántica HTTP / SEO |
| **Clasificación** | `SOFT_404` |
| **Estado** | **NO corregido en este ticket** — requiere una decisión de producto |
| **Medido** | 2026-09-01, build de producción local (`next build` + `next start`, Next 16.2.10) |

## Comportamiento observado

```
GET /medicamento/noesunslugvalido   → 200   <title>Medicamento no encontrado | PreciosFarma</title>
GET /ruta-que-no-existe             → 404   (control)
```

El slug de la prueba ni siquiera pasa `parseMedicationSlug`, así que no hay
búsqueda de por medio: la resolución falla de inmediato y aun así el status es
200. La URL "miente" para cualquier crawler y para cualquier monitor de
disponibilidad.

## Causa raíz, aislada experimentalmente

`notFound()` solo puede fijar el status **antes** de que Next haga flush de la
respuesta. Un `loading.tsx` crea un límite de Suspense que dispara ese flush
inmediatamente. Matriz de experimentos, cada fila con su propio `next build` +
`next start` + `curl`:

| Configuración | Status |
|---|---|
| `app/loading.tsx` + `app/medicamento/[slug]/loading.tsx` (producción actual) | **200** |
| Sin `app/medicamento/[slug]/loading.tsx` (queda el del segmento raíz) | **200** |
| `notFound()` desde `generateMetadata`, con los dos `loading.tsx` | **200** (también con User-Agent de Googlebot) |
| **Sin ningún `loading.tsx`** | **404** |

Conclusión: el responsable no es el `loading.tsx` de la ruta sino el del
**segmento raíz** (`web/src/app/loading.tsx`), que envuelve a todas las rutas
del sitio. Mover el `notFound()` a `generateMetadata` tampoco cambia nada — se
midió, y además haría perder el `noindex`, que hoy es lo único que contiene el
daño SEO.

## Por qué no se corrige acá

La única configuración que devuelve 404 exige **quitar el `loading.tsx` del
segmento raíz**, es decir dejar sin esqueleto de carga a todo el sitio. En esta
ruta concreta el costo es real y visible: la resolución ejecuta una búsqueda en
vivo contra 9 farmacias y tarda segundos, así que sin fallback el usuario ve una
página en blanco durante ese tiempo.

Cambiar el comportamiento de carga de todas las rutas del sitio es una decisión
de producto/UX, no una consecuencia técnica de este ticket
(CLAUDE.md §1 y §5). Se reporta para decisión CTO/Product en vez de asumirla.

**Opciones para esa decisión (no implementadas):**

1. Quitar `app/loading.tsx` y dar `loading.tsx` propio solo a las rutas que lo
   justifican (`/buscar/[query]` ya tiene el suyo), dejando `/medicamento/[slug]`
   sin fallback → 404 real, a cambio de segundos en blanco en la ficha.
2. Mantener el 200 y seguir conteniendo el daño con `noindex` (estado actual).
3. Reducir el tiempo de resolución hasta que el fallback deje de hacer falta —
   es lo que resolvería el registro persistido CFM-ID / RFC-002, que convierte la
   resolución en una lectura por identidad en vez de una búsqueda en vivo.

## Mitigación vigente

`generateMetadata` sigue devolviendo `robots: { index: false, follow: true }`
para toda ficha irresoluble. Es la única señal efectiva contra la indexación
mientras el status siga siendo 200, y hay un comentario en `page.tsx` que
explica por qué NO debe cambiarse por `notFound()`.

## Nota sobre el impacto real de este defecto

Después del fix de navegación, la cantidad de fichas irresolubles que un usuario
puede encontrar cae de 22/128 a 1/128 (ver `analysis/comparison.json`), así que
la superficie del soft-404 se reduce en la misma proporción. Sigue siendo
incorrecto, pero deja de ser frecuente.
